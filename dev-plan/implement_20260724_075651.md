## 문서 기반 제약 사항

- 신규 앱은 `com.thinktank.recorder.next`를 유지하고 기존 APK와 병행 설치한다.
- 녹음은 보이는 Activity에서 사용자가 명시적으로 시작한 경우에만 허용한다.
- `release`는 cleartext를 허용하지 않으며, debug의 로컬 HTTP 예외를 운영 빌드로
  확장하지 않는다.
- 현재 Receiver의 file/SQLite 구조를 Cloud Run 운영 환경에 그대로 배포하지 않는다.
- 업로드 완료는 HTTP 2xx가 아니라 로컬 identity와 서버 receipt 전체 일치로 확정한다.
- 진행 중 `.part` 파일과 검증되지 않은 orphan은 업로드하지 않는다.
- 실제 Android 14/15 장시간 검증과 운영 서명 없이는 내부 배포 완료로 처리하지 않는다.

## Phase 0. 운영 프로필·보존·개인정보 결정

### 목표

신규 앱이 실제 설치 환경에서 사용할 연결·보존·데이터 처리 정책을 구현 전에 고정한다.

### 구현 태스크

- [ ] 운영 기본 프로필은 public-CA HTTPS만 허용하는 `release`로 유지한다.
- [ ] LAN/VPN 내부 배포는 self-signed SPKI pin을 사용하는 별도 `internal` 프로필로
  구현하고, 운영 빌드에서 평문 HTTP를 허용하지 않는다고 확정한다.
- [ ] debug의 `10.0.2.2` HTTP 예외는 emulator 개발용으로만 유지한다.
- [ ] Receiver 자체서명 인증서 생성·pin 표시·앱 pin 입력/교체 절차를 계약으로 고정한다.
- [ ] 업로드 완료 파일의 기본 로컬 보존 기간을 승인한다. 기준안은 receipt 검증 후 7일이다.
- [ ] `FAILED`·`CONFLICT`·`QUARANTINED` 파일은 자동 삭제하지 않는다고 확정한다.
- [ ] 저장 공간 경고와 사용자 수동 정리에서 삭제 가능한 상태를 `UPLOADED`로 제한한다.
- [ ] 오디오 원본은 로컬에 남지만 전사 텍스트·주제 노트는 Claude 처리에 전송된다는

- [ ] 기존 APK 설치 안내와 신규 Compose 앱 설치 안내를 별도 문서/절로 분리한다.
- [ ] GCP persistent adapter는 이 계획 밖이며 public-CA URL만 받는다고 해서 현재
  Receiver를 Cloud Run에 배포 가능하다고 해석하지 않도록 문구를 고정한다.

## Phase 1. 파일 보존·저장 공간·crash 복구

### 목표

장기 녹음으로 저장 공간이 고갈되지 않고, 파일 확정 중 종료돼도 완료 파일을 잃지 않게 한다.

### 구현 태스크

- [ ] `RecordingDao`에 정리 대상 조회와 terminal file 상태 갱신 transaction을 추가한다.
- [ ] Room schema를 명시적으로 version-up하고 기존 v1 DB의 녹음·업로드·노트 상태를
  보존하는 migration을 구현한다. destructive migration은 사용하지 않는다.
- [ ] `UPLOADED`이며 server hash가 로컬 SHA-256과 일치하는 파일만 보존 기간 후 삭제한다.
- [ ] 파일 삭제 성공 후에만 Room에 삭제 시각/결과를 기록하고 재실행을 멱등하게 만든다.
- [ ] cleanup을 WorkManager unique work로 구현하고 앱 시작·주기 실행의 중복을 막는다.
- [ ] 녹음 시작 전 최대 청크 예상 크기와 안전 여유 공간을 확인한다.
- [ ] 녹음 중 디스크 부족은 현재 청크를 실패/격리 상태로 마감하고 사용자에게 조치 문구를
  제공한다.
- [ ] `.part` rename 성공 후 Room READY commit 전 종료된 경우 UUID·경로·hash를 확인해
  확정 파일을 기존 chunk에 승계한다.
- [ ] 원본 `.part`와 확정 파일이 함께 있거나 hash가 불일치하면 자동 승계하지 않고
  `QUARANTINED`로 보존한다.
- [ ] 수동 정리 화면에는 상태·크기·보존 만료만 노출하고 민감한 전체 파일 경로는 숨긴다.

### 자체 테스트

- [ ] READY·RETRY·UPLOADING·FAILED·CONFLICT·QUARANTINED 파일은 자동 삭제되지 않는다.
- [ ] v1 schema fixture를 신규 버전으로 migration한 뒤 row·FK·unique index가 보존된다.
- [ ] UPLOADED지만 server hash가 없거나 다른 파일은 삭제되지 않는다.
- [ ] 파일 삭제 성공/실패와 Room commit 전후 재실행이 같은 결과로 수렴한다.
- [ ] rename 전·후, SHA 계산 전·후, READY commit 전·후 crash matrix를 검증한다.
- [ ] 저장 공간 부족을 주입해 손상 파일 업로드가 0건인지 확인한다.
- [ ] AAC와 PCM/WAV 기준 1일·7일 예상 저장량을 UI/문서 수치와 대조한다.

### 이슈 및 수정

- [ ] OEM별 사용 가능 공간 오차는 삭제 범위를 넓히지 않고 안전 여유값으로 해결한다.

### 완료 조건

- [ ] 장기 사용 시 저장량 상한이 보존 정책으로 제어된다.
- [ ] crash 후 확정 파일이 READY 또는 명시적 격리 상태로 수렴한다.
- [ ] 자체 테스트가 완료됐다.
- [ ] Phase 2 진행이 가능하다.

## Phase 2. 동기화 상태·오류·알림 정합성

### 목표

사용자가 수동·자동 동기화의 실제 결과와 복구 방법을 앱에서 확인할 수 있게 한다.

### 구현 태스크

- [ ] WorkManager `WorkInfo`를 repository flow로 노출하고 수동 동기화의 queued/running/
  succeeded/retry/failed 상태를 Compose에 연결한다.
- [ ] 업로드 대기 수와 별도로 FAILED·CONFLICT·QUARANTINED 수와 최근 오류를 표시한다.
- [ ] `SyncRunResult`에서 업로드 성공과 노트 실패를 동시에 보존하고 성공으로 덮지 않는다.
- [ ] retryable/permanent/auth/conflict/storage 오류를 typed UI state로 매핑한다.
- [ ] 노트 동기화 결과를 서버 전체 노트 수가 아니라 신규·변경·보관된 수로 계산한다.
- [ ] 완료 알림은 실제 변경이 있을 때만 게시하고 동일 결과를 dedupe한다.
- [ ] manual work `KEEP`로 요청이 합류했을 때 이미 실행 중임을 사용자에게 표시한다.
- [ ] 자동 오디오 업로드와 노트 조회의 metered 정책을 분리해 Phase 0 결정과 맞춘다.
- [ ] WAV fallback은 `audio/wav`, M4A는 `audio/mp4`로 Content-Type을 전송한다.
- [ ] JSON 응답은 Content-Length 유무와 무관하게 실제 읽기 상한을 적용한다.
- [ ] `Retry-After`가 있는 429/503만 서버 지시를 따르고 나머지는 기존 backoff를 사용한다.

### 자체 테스트

- [ ] 수동 sync 성공·retry·401·409·413·507·DNS·timeout 결과가 UI와 Room에 일치한다.

- [ ] 노트가 존재하지만 변경이 없는 주기 sync에서 알림이 게시되지 않는다.
- [ ] manual+periodic 동시 실행에서 active claim과 active worker가 중복되지 않는다.
- [ ] WAV/M4A 요청 header와 server receipt를 MockWebServer·Receiver V1 fixture로 검증한다.
- [ ] chunked/잘못된 Content-Length/10MiB 초과 JSON 응답이 메모리 확장 없이 실패한다.

### 이슈 및 수정

## Phase 3. 노트 충돌 해결과 설정 UX

### 목표

### 구현 태스크

- [ ] `NoteConflict` 최신 항목을 repository/ViewModel flow로 노출한다.

- [ ] `로컬 유지`, `서버본 사용`, `직접 병합`의 세 가지 명시적 해결 action을 구현한다.
- [ ] 로컬 유지는 최신 서버 revision에 대해 사용자가 확인한 뒤 PUT하고, 서버본 사용은
  conflict와 DIRTY 상태를 transaction으로 정리한다.
- [ ] 직접 병합은 편집 초안을 로컬에 먼저 보존한 뒤 서버 저장을 시도한다.
- [ ] 설정 저장/연결 테스트/버전 확인 결과를 sealed UI message로 변경한다.
- [ ] 연결 테스트 실패 시 사용자가 `저장`을 누르지 않았다면 기존 정상 설정을 유지한다.
- [ ] 앱이 foreground에 있을 때 알림 deep link를 받아도 destination이 중복 적층되지 않게
  `onNewIntent` 또는 navigation event를 처리한다.
- [ ] deprecated `ClickableText`를 `LinkAnnotation` 기반 구현으로 교체한다.

### 자체 테스트

- [ ] 412 충돌 후 세 해결 action에서 로컬·서버·conflict row가 의도한 상태로 수렴한다.
- [ ] conflict 해결 중 네트워크 단절과 재충돌에서 두 본문이 모두 보존된다.
- [ ] 설정 저장 성공, 연결 성공, 연결 실패, 버전 확인 성공이 올바른 색·이미지로 표시된다.
- [ ] 잘못된 URL/token 연결 테스트가 기존 정상 설정을 덮어쓰지 않는다.
- [ ] 알림을 연속 탭해도 MainActivity와 note destination이 중복 생성되지 않는다.
- [ ] 위키링크 target/alias/없는 대상/동명 노트를 검증한다.

### 이슈 및 수정

- [ ] 자동 병합 알고리즘은 이 범위에 추가하지 않고 사용자 명시 선택만 제공한다.

### 완료 조건
