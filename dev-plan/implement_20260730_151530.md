# implement_20260730_151530.md

작성 일시: `2026-07-30 15:15:30 KST`

이 문서는 한 번 생성한 온디바이스 STT 전사문을 Qwen·EXAONE·Gemma에 동일하게
전달하고, 각 모델의 성공·거절·실패·Kotlin 대체 결과를 서로 덮어쓰지 않고 비교할 수
있도록 Android 로컬 AI 구조를 수정하는 개발 범위를 고정한다.

## 개발 목적

- 완료 녹음 한 건을 STT 한 번만 처리하고 이후 모델별 요약에서는 저장된 전사문을
  재사용한다.
- 같은 전사문뿐 아니라 같은 요약 입력 묶음과 입력 해시를 세 모델에 전달해 비교 조건을
  고정한다.
- Qwen·EXAONE·Gemma 실행 결과와 Kotlin fallback을 서로 다른 실행 기록으로 보존한다.
- 모델이 실패했는데 `EXTRACTIVE_KOTLIN` 결과로 덮어써져 실제 모델 실행 정보가 사라지는
  문제를 제거한다.
- 모든 로컬 모델 실패가 `QWEN_QUALITY_REJECTED`로 기록되는 모델 종속 오류 계약을
  제거한다.
- 파싱 성공 후 품질 거절된 후보와 파싱 실패 원인을 앱 내부 로컬 데이터로 보존해 모델별
  결과를 설명 가능하게 한다.
- 빈 제목·빈 요약·불완전 JSON을 정상 완료 또는 해당 LLM 성공으로 표시하지 않는다.
- STT의 “음원 전체 범위 처리 완료”와 “언어 인식 품질 양호”를 분리해 표시하고 측정한다.
- 외부 서버·클라우드·네트워크 추론 없이 Samsung 실기기에서 전체 흐름을 검증한다.

## 문서 기반 제약 사항

- 현재 Room DB 버전은 `7`이며 기존 사용자 세션과 STT 진단 필드를 보존해야 한다.
- 기존 `ondevice_sessions`는 세션 상태와 선택된 최신 결과를 함께 저장하므로 한 모델의
  실패 후 fallback 결과가 모델 메타데이터를 덮어쓸 수 있다.
- 현재 `QwenInferenceService`라는 역사적 클래스·AIDL 이름은 instrumentation 및 manifest
  호환을 위해 당장 변경하지 않되, 내부 결과 계약은 모델 중립적으로 바꾼다.
- Qwen·EXAONE은 llama.cpp 경로에서 grammar와 생성 설정을 적용할 수 있다.
- Gemma LiteRT-LM 경로는 현재 `GenerationRequest.maxTokens`와 grammar를
  `GemmaLiteRtBridge.generate()`에 전달하지 않는다.
- 기존 계획의 원문·모델 raw 출력 비노출 규칙은 유지한다. 모델 출력은 앱 내부 로컬 DB와
  사용자 화면에서만 확인하고 logcat·PC 증적·계획 문서·서버에는 기록하지 않는다.
- 설치된 모델과 다운로드 artifact는 사용자가 명시적으로 삭제하지 않는 한 유지한다.
- 모델 비교는 메모리와 발열을 제한하기 위해 병렬이 아니라 한 번에 한 모델씩 실행한다.

## 핵심 설계 결정

### 저장의 기준

- `ondevice_sessions.transcript`를 현재 작업의 불변 전사 원본으로 유지한다.
- 새 `ondevice_summary_batches`는 동일 입력 비교 한 회를 나타낸다.
- 새 `ondevice_summary_runs`는 batch 안의 모델 또는 fallback 실행 한 회를 나타낸다.
- 기존 세션의 title/summary/actionItems 필드는 사용자가 선택한 결과를 표시하는
  호환 projection으로 유지한다.
- 기존 세션은 자동 backfill하지 않고 새 비교·재요약 실행부터 새 테이블을 사용한다.

### 요약 비교 batch

`ondevice_summary_batches`에는 최소 다음 정보를 저장한다.

- batch ID, session ID, 생성·완료 시각, batch 상태
- 원본 전사 `sourceHash`
- 공통 요약 입력 `inputHash`
- 공통 입력 생성 정책 `inputBuilderVersion`
- 모델에 전달한 공통 입력 payload
- 요청 모델 목록과 실행 순서
- 선택된 최종 run ID
- 로컬 전용 data policy

### 모델별 run

`ondevice_summary_runs`에는 최소 다음 정보를 저장한다.

- run ID, batch ID, session ID, 실행 순서
- `requestedEngine`, `attemptedEngine`, model ID/version, runtime, generation profile
- `RUNNING/PASSED/QUALITY_REJECTED/SCHEMA_REJECTED/RUNTIME_FAILED/CANCELLED`
  실행 상태
- `EVIDENCE_SELECTION/SUMMARY_GENERATION/JSON_PARSING/QUALITY_VALIDATION/FALLBACK`
  실패 단계
- title, summary items, action items와 문장별 evidence ID
- violation code, 모델 중립 failure code
- 시작·완료·실행 시간, 입력/출력 글자 수, 가능하면 token 수
- raw output 길이·SHA-256·잘림 여부
- 앱 내부에서만 확인할 수 있는 최대 8KB raw output
- fallback 대상 원본 run ID
- operation token

### raw output 보존 정책

- raw output은 앱 내부 DB에만 저장하고 외부 로그·문서·서버·동기화 payload에 포함하지 않는다.
- 최대 8KB를 넘으면 앞부분을 임의 성공 후보로 사용하지 않고 `rawOutputTruncated=true`로
  기록한 뒤 schema 실패로 종료한다.
- 녹음/세션 삭제 시 관련 batch/run과 함께 삭제한다.
- 사용자가 비교 결과 삭제를 명시한 경우에만 해당 batch/run을 삭제한다.
- 일반 노트·아카이브 화면에는 노출하지 않고 로컬 AI 비교 상세에서만 펼쳐 볼 수 있게 한다.

### fallback 정책

- LLM run의 엔진과 상태는 fallback 결과로 변경하지 않는다.
- Kotlin fallback은 `fallbackForRunId`를 가진 별도 run으로 저장한다.
- fallback도 품질 검사를 통과해야 `FALLBACK_PASSED`가 된다.
- 빈 fallback은 `FALLBACK_EMPTY`로 남기고 정상 요약으로 선택하지 않는다.
- 세션의 기존 summary projection은 `PASSED` 또는 `FALLBACK_PASSED` run을 사용자가
  선택했을 때만 갱신한다.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- 구현 중 발생한 이슈는 해당 Phase에서 수정하고 기록한다.
- 체크박스 상태를 실제 진행 상태와 맞게 업데이트한다.
- 문서에 없는 기능·모델·서버 연동·리팩터링을 추가하지 않는다.
- 한 기능은 유지보수 가능한 최소 책임 단위로 나누고 역할과 경계를 지킨다.
- 공통화는 세 모델의 중복 계약을 줄일 때만 수행하고 기존 전체 구조를 재작성하지 않는다.
- 기존 프로젝트 API·Room·Coroutines·공식 모델 SDK를 우선 사용하고 새 의존성을 추가하지 않는다.
- 비교 실행 중에는 모델을 병렬 load하지 않고 기존 `ResourceArbiter` 안에서 직렬화한다.
- 모델별 자동 교정은 최대 1회, 전체 모델별 실기기 반복은 최대 3회로 제한한다.
- 실패 원문·raw output을 logcat, Gradle 출력, PC 파일, 계획 문서에 기록하지 않는다.
- 추론 중 네트워크 사용을 금지하고 모델 다운로드만 기존 Wi-Fi 정책을 유지한다.
- 기존 녹음 원본은 읽기 전용으로 사용하고 분석용 임시 파일만 작업 종료 후 정리한다.
- `.qa` 설치는 동일 서명 APK의 `adb install -r`만 사용한다.
- 자동 instrumentation은 `.deviceTest` 격리 패키지에서만 실행한다.
- 실기기 명령은 Samsung `R3CY40PXCAP`만 허용하고 PD20은 항상 제외한다.
- 빈 요약, 파싱되지 않은 부분 JSON, 품질 거절 결과를 정상 LLM 성공으로 표시하지 않는다.
- migration 이후에도 구버전 컬럼과 화면을 읽을 수 있게 유지하며 파괴적 schema 변경을 금지한다.

|---|---|---|
| 같은 STT 입력 사용 | 세 모델 모두 동일 `sourceHash/inputHash`, 공통 payload 600자 | 충족 |

#### 원인

1. **완료 기준을 잘못 정의했다.**
   `SummaryComparisonCoordinator`는 LLM이 실패한 뒤 생성한 Kotlin fallback도
   `passedRunIds`에 넣는다. 화면과 작업 보고가 “사용 가능한 결과가 생김”을
   “로컬 LLM 요약이 성공함”으로 확대 해석했다. 최종 선택 결과도
   `attemptedEngine=EXTRACTIVE_KOTLIN`, `runtimeType=KOTLIN`이며 LLM 결과가 아니다.
2. **진짜 한 번의 E2E 재시험이 아니었다.**
   인식 품질 `NOISY`가 저장된 새 세션과 수정 후 3모델 비교에 사용한 이전 세션이 다르다.
   두 세션은 동일 원본과 동일 1,943자 전사를 가지지만, 비교 세션의
   `sttRecognitionQualityStatus`는 `NULL`이다. 기존 세션 진단 backfill도 없고 비교 시작
   시 품질 재평가도 하지 않으므로, 품질 경고가 요약 실행 조건에 반영되지 않았다.
3. **STT는 끝까지 처리됐지만 문장 품질은 좋지 않았다.**
   `312,128/312,128ms`, `13/13`은 범위 완료 증거일 뿐 정확도 증거가 아니다. 동일 전사를
   새 evaluator로 평가한 결과는 `NOISY`, 최대 무구두점 구간 351자로 기준 240자를
   넘었다. 기준 전사문이 없어 CER/WER는 아직 측정하지 못했다.
4. **0.8B~1.2B int4 모델 능력과 출력 계약이 맞지 않았다.**
   모델은 최대 2개, 항목 80자/전체 100자, 완결형 문장, 근거 토큰 30% 이상,
   제목 근거 50% 이상, 미지원 숫자·영문 금지, evidence ID 포함 JSON을 한 번에
   만족해야 한다. 후처리 전 실제 결과는 Qwen이 길이·근거·영문 조건, EXAONE이
   제목·문장 완결·근거 조건, Gemma가 항목 수·길이·완결·제목 근거 조건에서 탈락했다.
5. **공통 입력 준비가 2단계 파이프라인을 우회한다.**
   `SummaryInputBuilder`가 만든 prepared payload는 모델별 evidence 선택 단계를 건너뛰고
   4개 구간을 전부 요약 단계에 넘긴다. 작은 모델이 핵심 선택, 압축, 근거 연결,
   JSON 준수를 한 생성에서 동시에 수행한다.
6. **복구 범위가 실제 실패 형태보다 좁다.**
   재생성은 1회뿐이다. EXAONE 제목 복구는 제목 관련 위반만 있을 때 동작하지만 실제
   결과에는 `BULLET_TOO_SHORT`, `INCOMPLETE_BULLET`, `WEAK_SOURCE_EVIDENCE`가 함께 있어
   적용되지 않았다. Qwen과 Gemma도 본문 위반이라 제목 복구 대상이 아니다.
7. **Gemma 구조 제약은 런타임상 약하다.**
   llama.cpp 모델에는 GBNF를 적용하지만 LiteRT-LM Gemma 경로에는 공개 GBNF API가 없어
   프롬프트와 사후 parser/gate에 의존한다. 입력 축소 후 JSON 파싱은 성공했지만 4개
   항목을 출력해 최대 2개 규칙을 어겼다.

따라서 현재 달성된 것은 **실패 기록 보존, 동일 입력 재현, 안전한 Kotlin fallback,
원본·모델 보존**이다. 달성되지 않은 것은 **각 로컬 LLM이 직접 만든 통과 요약의 비교**다.
향후 완료 판정은 fallback을 제외하고
`attemptedEngine in (QWEN_LOCAL, EXAONE_LOCAL, GEMMA_LOCAL) AND state=PASSED`를
모델별로 확인해야 한다.

## Phase 10. Gemma 5분 결과 재감사·오탐 제거·동일 조건 재현

### 재감사 정정

- 2026-07-31 이전의 `Gemma 3/3` 기록은 현재 기준의 재현 성공 증거로 사용하지 않는다.
  동일 원본이었지만 input builder·prompt·generation profile이 달랐고, 일부 run은
  긴 배열에서 첫 문장만 건진 parser salvage 또는 일반적인 한 문장으로 통과한 오탐이었다.

- 따라서 동일 파일·동일 source hash만으로 성공을 주장하지 않고, builder/profile/runtime/
  fallback/원문 출력/최종 문장 품질을 함께 확인한다.

## 잔여 리스크 / 후속 과제

- 현재 5분 입력에서는 세 모델 3/3 통과를 확인했지만 다른 화자·잡음·전문용어 분포까지
  일반화된 것은 아니다. 향후 고정 정답 fixture로 모델별 통과율과 내용 정확도를 계속
  회귀 측정한다.
- SenseVoice의 한국어 고유명사·구어체 정확도는 범위 완전성 수정과 별개의 모델 품질
  문제다. CER/WER 기준선 이후에만 모델 교체 또는 추가 후처리를 검토한다.
- LiteRT-LM 공개 API에서 원하는 token/stop 제어를 직접 제공하지 않으면 bridge 수준의
  출력 감시·취소 가능 범위를 확인하고 별도 제한을 문서화한다.
- Room v8 적용 뒤 구버전 APK로의 단순 downgrade는 지원하지 않는다. rollback은 데이터
  삭제가 아니라 v8 schema를 읽는 수정 APK 재배포 방식으로 수행한다.
- raw output은 로컬 비교에 필요하지만 전사 내용을 포함할 수 있다. 향후 외부 export나
  동기화 요구가 생기면 이번 범위에 추가하지 않고 별도의 사용자 동의·암호화 계획을 만든다.
