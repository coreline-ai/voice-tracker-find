## 개발 목적

기존 `thinktank-recorder.apk`의 핵심 흐름인 **녹음 → 로컬 보관 → 서버 업로드 → 서버 처리 → 노트 확인**을 Kotlin Android 네이티브 앱으로 재구현한다.

Jetpack Compose로 UI를 구성하고, 녹음·Foreground Service·Room·WorkManager·Android Keystore까지 Kotlin 단일 코드베이스에서 구현하여 Flutter platform channel과 이중 상태 관리 복잡도를 제거한다.

| 이름만으로 `_find_note()` | 다른 폴더의 동명 노트 구분 불가 | **E** | 서버 note id 도입 또는 `(folder,name)` 계약으로 변경 |

| 기존 기능과 코드 근거 | 현재 동작 | 분류 | Compose 계획 |

| call folder `Recordings/Call`, `Call`, `Sounds` | 최근 1~30일의 m4a/mp3/wav/ogg 업로드 | **C/D** | V1 제외; internal flavor + SAF/명시적 폴더 선택으로만 후속 검토 |

| 1차 행동 | 녹음 시작·정지 |
| 2차 행동 | 업로드 상태 확인, 생성된 노트 읽기·편집 |

| 피해야 할 인상 | AI 챗봇, 암호화폐, 네온 SaaS, 과장된 미래 기술, 템플릿형 카드 대시보드 |

### 웹 레퍼런스 조사 결과

조사한 화면은 패턴 분석에만 사용하며 시각 요소를 직접 복제하지 않는다.

| 레퍼런스 | 참고할 점 | 복제하지 않을 점 |
|---|---|---|
| Google Recorder | 큰 녹음 시간, 파형, 하나의 명확한 주 동작, 녹음/재생 상태 위계 | Pixel 고유 색·아이콘·레이아웃 |
| Bear | Markdown 본문 가독성, 따뜻한 테마, 편집 도구가 본문을 방해하지 않는 방식 | Bear 색상·일러스트·태그 구조 |
| Voicenotes | 녹음에서 노트로 이어지는 단순한 mental model | “AI 마법” 중심 카피와 일반적인 AI 그라데이션 |
| Material 3 | Compose component, 상태·접근성·system UI 연동 | 기본 component를 그대로 늘어놓은 템플릿형 화면 |

### 비-AI 시각 원칙

- 무작위 보라/파랑 그라데이션, 발광 구, 별 반짝이, 유리 카드, 무의미한 3D 로봇을 사용하지 않는다.
- 모든 섹션을 둥근 카드로 감싸지 않는다. 배경·여백·타이포그래피·1px divider로 정보 구조를 먼저 만든다.
- 이미지에는 텍스트·가짜 파형·가짜 UI를 넣지 않는다. 실제 상태와 데이터는 Compose가 그린다.
- 녹음 파형은 이미지 에셋이 아니라 실시간 데이터 기반 Canvas로 표시한다.
- 이미지 에셋은 hero, onboarding, empty/error state에만 사용하고 기능 버튼의 의미를 대신하지 않는다.
- 생성형 이미지를 사용하더라도 동일 art direction으로 수동 선별·보정하고 손, 글자, 로고, 비현실적 물체가 있는 결과는 폐기한다.
- 타 앱 스크린샷, 브랜드 로고, 유료 스톡 미리보기 이미지를 제품 에셋으로 포함하지 않는다.

### 컬러 시스템

기본 테마는 브랜드 고정 palette를 사용하고 Material dynamic color는 V1 기본값에서 끈다. 색상 값은 contrast 측정 후 조정 가능하지만 역할은 변경하지 않는다.

- UI/숫자/상태: `Pretendard Variable` 400/500/600/700.

- Body 16sp/24sp line height, secondary 13~14sp, screen title 28~32sp, hero time 48~56sp 범위로 시작하고 font scale 200%에서 재검증한다.
- 글꼴 파일과 OFL/배포 라이선스를 `ASSET_LICENSES.md`에 포함한다.

### 에셋 소싱·권리 규칙

- 최종 에셋은 맞춤 제작/의뢰, 직접 촬영, 또는 상업적 앱 배포가 명확히 허용된 원본만 사용한다.
- 웹에서 찾은 Google Recorder/Bear/Voicenotes 이미지는 reference board에 링크만 기록하고 제품 번들에 넣지 않는다.
- 각 파일은 `source`, `author`, `license`, `downloaded/generatedAt`, `modification`, `SHA-256`을 asset manifest에 기록한다.
- 생성형 에셋은 model/tool, prompt, 생성 일시, 수동 보정 내역을 기록하고 제3자 로고·유명 제품·텍스트가 포함된 결과를 제외한다.
- 라이선스 증빙이 없는 파일은 debug mockup에도 커밋하지 않는다.

### 화면 레이아웃 전략

#### 녹음 탭

1. 상단 38~42%에 `hero_recording_chamber`를 full-bleed crop하고 아래쪽을 archiveInk로 자연스럽게 fade한다.
2. hero 위에는 상태 문장 한 줄과 녹음 시간을 배치하되 이미지 대비가 부족하면 고정 scrim을 사용한다.
3. 하단에는 176~200dp 크기의 물리 버튼을 연상시키는 record control 하나만 강하게 둔다.
4. 파형은 버튼 위 또는 시간 아래의 얇은 sound thread로 표현하고 실제 amplitude만 반영한다.
5. 저장 위치·현재 청크·업로드 큐는 접을 수 있는 진단 panel로 낮은 우선순위에 둔다.

#### 노트 탭

1. 폴더 그룹은 카드 묶음 대신 editorial section label과 hairline divider로 나눈다.
2. 목록은 제목, 2줄 preview, 수정 시각, sync state만 보여주고 random thumbnail을 만들지 않는다.
3. note 상세는 `archivePaper` 표면과 MaruBuri heading, Pretendard body로 읽기 경험을 우선한다.
4. WikiLink는 구리색 밑줄과 link icon/semantics를 함께 제공한다.
5. 노트가 없을 때만 `empty_notes_desk`와 짧은 안내를 사용한다.

#### 설정 탭

1. hero 이미지 없이 밀도 높은 native setting list를 사용한다.
2. 녹음·동기화·서버·권한·앱 정보로 section을 나누고 모든 항목을 카드로 만들지 않는다.
3. destructive 또는 민감한 설정은 하단에 분리하고 현재 값·오류를 보조 문장으로 표시한다.

### 모션 원칙

- 화면 전환 180~240ms, record 상태 전환 220~320ms 범위의 restrained motion을 사용한다.
- 지속적인 glow/pulse는 사용하지 않고 녹음 중에는 sound thread의 실제 amplitude와 작은 상태 dot만 움직인다.
- 시스템 animator duration scale 0 또는 reduced motion에서는 파형을 정적 level meter와 텍스트 상태로 대체한다.
- 이미지 parallax, 자동 슬라이드, 장식용 Lottie는 V1에서 사용하지 않는다.

Kotlin Compose 전환으로 제거되는 구성은 `pubspec.yaml`, Dart feature 계층, MethodChannel/EventChannel, Flutter 플러그인 호환성 검증이다. Android 운영체제의 microphone foreground service 제한은 UI 기술과 무관하므로 그대로 적용한다.

## 문서 기반 제약 사항

1. 저장소에는 기존 APK의 Kotlin/Java 원본과 Gradle 프로젝트가 없다. 신규 구현이 원칙이다.
2. 기존 APK의 applicationId는 `com.thinktank.recorder`이고, 동일 패키지 업데이트에는 기존 서명 개인키가 필요하다.
3. 서명 키가 확인되지 않으면 V1 applicationId는 `com.thinktank.recorder.next`로 하며 기존 앱과 병행 설치한다.
4. Android 14+에서 microphone foreground service는 앱이 사용자에게 보이는 상태에서 시작해야 한다.
5. WorkManager 실행 시각은 운영체제 전원·네트워크 조건에 따라 지연될 수 있다.
6. 원격 연결은 HTTPS 또는 VPN을 전제로 한다. Compose 전환 자체가 서버를 인터넷에 노출하지는 않는다.

**진전:** 2차 검토 P1 총 10건(서버 5 + Android 5)이 **전부 코드+전용 회귀 테스트로 해소**됐다. Android 계획 준수도 75~80% → 약 90%, 서버 신규 안전 V1 대응률(개별 갭 기준) 94% → 약 99%. 대시보드 보안(인증·path traversal·XSS·토큰 비노출)은 코드 수준에서 실제 준수 확인.

**그러나 3차에서 배포 차단급 신규 결함 2건을 발견 — 판정은 CONDITIONAL(선행 조건부):**

1. **[서버 P0 · 실증] HTTP 응답 헤더 삽입(CRLF injection)** — [receiver.py:688](../src/thinktank/receiver.py#L688)의 `POST /api/v1/notes/{userId}` Location 헤더가 unquote된 경로 세그먼트를 검증 없이 반영한다. 같은 클래스 `_request_id()`([:265-278](../src/thinktank/receiver.py#L265-L278))는 CR/LF·제어문자를 거르는데 이곳만 누락. 단일 사용자 모드(기본 배포)에서 유효 Bearer 토큰만으로 `Set-Cookie` 등 임의 헤더 주입이 raw-socket PoC로 실증됨(CWE-113). 조치: Location을 인증으로 확정된 `user.name`으로 구성하거나 `_request_id()`식 검증 적용.
2. **[서버 P1 · 재현] "삭제한 노트가 목록에서 사라진다" 계약 붕괴** — HEAD `3e4656d`에서 `NOTE_SPECS`([:88-96](../src/thinktank/receiver.py#L88-L96))에 `("90-archive", 100, None)`가 무필터로 추가돼 보관 노트가 legacy `/notes/{user}` 목록에 재노출. 회귀 테스트 `test_삭제한_노트는_목록에서_사라진다`가 현재 **RED**(오케스트레이터 재현 확인). `_collect_notes`가 legacy·V1 공유라 legacy 계약까지 파급. 조치: legacy 필터 복원 또는 "legacy도 노출" 확정+테스트 갱신, 결정 기록.

**수치 정정:** 서버 회귀는 계획서 표기(2026-07-24 04:10 절의 "575 passed", `implement_20260724_163736.md`의 "635 passed")와 달리 현재 HEAD 실측 **597 passed / 1 failed / 4 skipped / 4 deselected**다(6개 지정 파일 기준 136 passed / 1 failed). Android는 마지막 단위 테스트 증적(07-24 03:21, 22건 통과) 이후 커밋 2건에서 main 9파일 수정+테스트 11건 추가됐으나 그 상태의 실행 증적이 `build/`에 없어 재실행이 필요하다.

### 구현 태스크

- [ ] 구현 전에 legacy APK와 신규 Compose 클라이언트의 요청·응답 fixture 및 OpenAPI 또는 동등한 계약 문서를 작성하고 실패하는 RED 계약 테스트를 먼저 커밋한다.
- [ ] 기존 `/upload`, `/notes`, `/apk/info`, `/apk` 경로와 plain 응답은 migration 기간 동안 유지하고 신규 안전 계약은 `/api/v1` 하위에 additive하게 구현한다.
- [ ] legacy API 제거 시점과 사용량 확인 방법을 Phase 0 결정 기록에 연결한다.
- [ ] 현재 `PUT /upload/{user}/{filename}` 인증·헤더·크기·확장자 계약을 테스트로 고정한다.
- [ ] 신규 versioned upload 요청에 client uploadId, recordingId, chunkId, `X-Content-SHA256`, `Content-Length`를 필수 계약으로 정의한다.
- [ ] 신규 upload receipt를 `uploadId`, `recordingId`, `chunkId`, `filename`, `size`, `sha256`, `status`, `receivedAt` 필드로 고정한다.
- [ ] ingest 파일이 처리·삭제된 뒤에도 receipt가 남는 영속 upload ledger를 구현하고 모든 PK/unique 제약을 `userId` 범위로 제한한다. 사용자 간 hash dedupe는 하지 않는다.
- [ ] 같은 userId+uploadId+hash 재전송은 기존 receipt와 `200`, 신규 저장은 `201`, 같은 uploadId 또는 이름의 다른 hash는 `409`로 처리한다.
- [ ] 요청마다 UUID 기반 임시 파일을 사용하고 DB unique constraint 또는 per-upload lock으로 병렬 PUT을 직렬화한다.
- [ ] body를 streaming hash하고 선언 size/hash와 검증한 뒤 파일 flush/fsync, 원자적 replace, ledger commit 순서를 고정한다.
- [ ] 0-byte, Content-Length 누락/오류, 선언 길이보다 짧거나 긴 body, 끊긴 전송, stale temp 정리 정책을 구현한다.
- [ ] 노트 목록 응답에 안정적인 note id, folder, updatedAt, revision을 추가한다.
- [ ] note id 생성·rename·archive 후 안정성 규칙을 정의한다. opaque id 저장소를 구현하지 않으면 rename은 V1에서 제외한다.
- [ ] 노트 수정은 note id와 `If-Match` revision을 받고, 헤더 누락은 `428`, stale revision은 `412`, 성공은 새 ETag를 반환한다.
- [ ] revision 비교와 임시 파일 write/flush/fsync/replace를 동일 per-note 임계구역에서 수행한다.
- [x] 노트 경로를 resolve한 뒤 사용자 vault 내부인지 확인해 symlink를 통한 외부 read/write를 차단한다.
- [ ] 새 노트를 V1에 포함하면 `POST /notes/{user}` create 계약을 추가하고, 포함하지 않으면 앱의 새 노트 기능을 제거한다.
- [ ] 노트 삭제는 id/revision 기반 archive/tombstone 계약으로 변경하고 DELETE 재시도의 멱등 결과를 정의한다.
- [x] `/apk/info`를 versionCode, versionName, sha256, size, releaseNotes를 가진 JSON으로 정의한다.
- [x] APK 다운로드를 V1에 포함하면 Bearer header 또는 짧은 수명 일회성 token 계약을 추가하고 장기 token query 사용을 제거한다.

## Phase 3. 데이터·보안·네트워크 기반

### 구현 태스크

- [ ] Room entity/DAO로 Recording, Chunk, UploadAttempt, Note, SyncCursor 상태를 정의한다.
- [ ] `RecordingSession 1:N Chunk`, `Chunk 1:N UploadAttempt`, `Note 1:N NoteConflict` 관계와 userId/serverProfileId 범위를 schema로 고정한다.
- [ ] Chunk 상태전이를 `RECORDING → FINALIZING → READY → CLAIMED → UPLOADING → UPLOADED`로 제한하고 실패·격리·lease 만료 전이를 별도로 정의한다.
- [ ] Room unique index, foreign key, transaction 경계를 사용해 한 Chunk가 동시에 한 active upload claim만 갖게 한다.
- [ ] Repository가 Room을 단일 진실 공급원으로 노출하게 한다.
- [ ] 기존 `uploaded_files` 파일명 Set을 사용하지 않고 recording UUID + size + SHA-256으로 전송 원장을 설계한다.
- [ ] 일반 설정은 DataStore, 토큰 암호화 키는 Android Keystore로 관리한다.
- [ ] token은 Keystore key alias로 암호화한 AEAD ciphertext로 저장하고 key invalidation·기기 복원·재로그인 흐름을 정의한다.
- [ ] `allowBackup=false` 또는 data extraction rules로 token, pin, Room DB, 녹음 파일을 cloud/device backup 대상에서 제외한다.
- [ ] OkHttp client에 Bearer 인증, streaming PUT, 타임아웃, TLS 검증을 구현한다.
- [ ] LAN 개발 HTTP는 debug 구성에서만 허용한다.
- [ ] 공개 CA HTTPS는 기본 trust/hostname 검증을 사용하고, self-signed pin 모드는 저장된 특정 host에만 제한한다.
- [ ] redirect로 host/scheme이 바뀌는 요청은 인증 헤더 전달 전에 거부한다.
- [ ] 서버 URL·사용자·토큰·Wi-Fi 우선 설정과 연결 테스트를 구현한다.
- [ ] 동일 package migration이 승인된 경우에만 기존 `recorder_prefs`, 파일, uploaded filename Set을 일회성 importer로 읽고 migration 완료 marker를 원자적으로 저장한다.
- [ ] 신규 package 기본안은 기존 private data 자동 import를 시도하지 않고 설정 재입력·선택적 파일 import UX만 노출한다.

## Phase 6. 파일 분할·복구·업로드 동기화

### 목표

### 구현 태스크

- [ ] 기본 20분·최소 5분 청크와 UTC timestamp + UUID 파일명을 구현한다.
- [ ] 진행 파일은 `.part`, 완료 파일은 원자적 rename으로 구분한다.
- [ ] 완료 파일의 크기·SHA-256을 Room에 기록한다.
- [ ] MediaRecorder가 열고 있는 현재 청크는 파일 확장자나 디렉터리 검색만으로 업로드 후보가 되지 않게 한다.
- [ ] 앱 시작 시 DB와 파일 시스템을 대조해 중단 파일을 복구 또는 격리한다. 비정상 종료 MP4의 playable salvage는 보장하지 않고 검증 실패 orphan은 업로드 금지한다.
- [ ] UploadWorker에 네트워크·unmetered 제약과 지수 backoff를 적용한다.
- [ ] manual/periodic sync가 공유하는 unique work name, `ExistingWorkPolicy`, enqueue 합류 규칙을 고정한다.
- [ ] READY→CLAIMED를 Room transaction/CAS로 처리하고 owner worker id, claimedAt, leaseExpiresAt을 저장한다.
- [ ] worker 종료·프로세스 kill 후 만료 lease를 READY로 회수하되 이미 receipt가 있으면 UPLOADED로 수렴한다.
- [ ] 수동 동기화와 자동 동기화를 분리하고, 자동 오디오 업로드만 unmetered를 기본값으로 적용한다.

- [ ] Worker는 retryable 장애에서 `Result.retry()`, 설정·인증·충돌 문제에서 영구 실패 상태를 반환한다.
- [ ] 성공 응답의 server hash가 로컬 hash와 일치할 때만 Uploaded로 확정한다.
- [ ] 파일 rename, Room FINALIZING→READY, Worker 조회 사이 모든 crash 지점의 reconcile matrix를 문서화하고 구현한다.
- [ ] 자동 삭제는 하지 않되 저장 공간 경고 임계치, 사용자 수동 삭제 조건, Uploaded 파일만 삭제 가능하다는 보존 정책을 구현한다.
