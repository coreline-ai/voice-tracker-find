## 개발 목적

기존 `thinktank-recorder.apk`의 핵심 흐름(녹음 → 로컬 보관 → 서버 업로드 → 서버 처리 → 노트 확인)을 **Android 전용 Flutter 앱**으로 재구현한다. UI와 업무 상태는 Flutter/Dart로 구성하고, Android 운영체제 권한·녹음·포그라운드 서비스·백그라운드 작업은 Kotlin 네이티브 계층으로 구현한다.

목표는 기존 APK의 바이트코드 또는 APK를 변환하는 것이 아니라, 검증된 서버 HTTP 계약을 유지하면서 유지보수 가능한 신규 앱을 만드는 것이다.

## 현재 분석 기준과 제약

1. 저장소에는 Flutter/Android 원본(`pubspec.yaml`, Gradle, Kotlin/Java)과 기존 APK의 서명 키(`.jks`, `.keystore`, `key.properties`)가 없다. APK는 재구현 참고용으로만 사용한다.
2. 현 APK 패키지명은 `com.thinktank.recorder`이며 기존 설치본과 동일 패키지로 업데이트하려면 동일한 서명 개인키가 필요하다. 키가 없으면 신규 앱 ID로 병행 설치해야 한다.
3. Android 14 이상에서 마이크 권한은 앱이 보이는 상태일 때 foreground service를 시작하는 방식으로 설계해야 한다. `BOOT_COMPLETED`, watchdog, 백그라운드 알람만으로 마이크 서비스를 다시 올리는 동작은 제품 요구로 약속하지 않는다.
4. WorkManager의 주기 작업은 지연될 수 있는 최선 노력 작업이다. 녹음 중인 실시간 업로드나 정확한 30분 실행 수단이 아니다.
5. 현재 서버 업로드는 `PUT /upload/{user}/{filename}`에 `Authorization: Bearer`, raw body, `Content-Length`를 보내며, 성공 뒤 서버가 처리 파이프라인을 실행한다. 이 계약은 호환 유지하되 충돌 판정은 강화한다.

## 공통 진행 규칙

1. 기능 단위로 Dart와 Kotlin의 인터페이스 계약을 먼저 문서화하고 mock 테스트를 작성한다.
2. Android 권한은 최소 권한을 원칙으로 하며, `RECORD_AUDIO`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE_MICROPHONE` 외 권한은 근거와 배포 채널을 명시한다.
3. 마이크 녹음 시작은 항상 사용자가 보이는 Activity에서 누르는 동작을 기점으로 한다.
4. 파일은 `.part` → fsync/종료 → rename 방식으로 완료 상태를 구분한다. 업로드 대상은 완료 파일만 허용한다.
5. 네트워크·권한·서비스 종료 오류는 사용자가 회복할 수 있는 상태와 안내 문구로 노출한다. 예외를 삼키고 성공으로 표시하지 않는다.
6. 서버의 기존 데이터를 변경·삭제하는 테스트는 격리된 테스트 디렉터리와 테스트 사용자로만 실행한다.
7. 실제 기기에서 Android 14와 Android 15(가능 시)를 모두 검증하고, 에뮬레이터 통과만으로 완료 처리하지 않는다.
8. 서명 키·Bearer token·TLS 핀·실서버 주소는 저장소 또는 로그에 넣지 않는다.

### 목표

### 구현 작업

- [ ] 기존 APK 서명 개인키의 보유 여부와 접근 권한을 담당자에게 확인한다.
- [ ] 키 미제공 기본안으로 신규 applicationId `com.thinktank.recorder.flutter`를 승인한다.
- [ ] 기존 사용자에게는 신규 앱 병행 설치 및 외부 녹음 파일 보존 안내를 제공한다.
- [ ] 초기 배포를 사내 APK/테스터 배포로 확정하고 Play 배포 여부를 별도 체크포인트로 분리한다.
- [ ] 사용자 시작 녹음, Wi-Fi 우선 업로드, 원격 URL 설정을 V1 핵심 기능으로 확정한다.
- [ ] 부팅 자동 마이크 시작, exact-alarm watchdog, 전체 저장소 스캔을 V1 제외로 기록한다.
- [ ] GCP/VPN/LAN은 동일 HTTPS base URL 계약으로 연결한다는 네트워크 원칙을 확정한다.

### 자체 테스트

- [ ] 기존 APK 패키지명·서명 인증서·키 부재 근거를 배포 기록에 첨부한다.
- [ ] 신규 ID APK와 기존 APK가 같은 시험 기기에 동시에 설치되는지 확인한다.

- **기존 앱을 덮어써야 하는 요구**: 기존 서명 개인키 없이는 기술적으로 불가능하다. 키를 확보하거나 신규 앱 전환 절차를 선택한다.

## Phase 2 — 서버 업로드 계약과 수신기 안전성 보강

### 목표

새 클라이언트가 재시도해도 데이터가 손상·중복되지 않도록 현행 수신기를 명확한 멱등 계약으로 보강한다.

### 구현 작업

- [ ] `receiver.py`의 `PUT /upload/{user}/{filename}` 계약(인증, 허용 확장자, Content-Length, 크기 한도)을 API 문서로 고정한다.
- [ ] 파일명만 같을 때 무조건 성공을 반환하는 현재 동작을 검토하고, SHA-256 또는 업로드 세션 ID 기반 중복 판정을 설계한다.
- [ ] 동일 파일 재전송은 명시적 idempotent 성공, 다른 콘텐츠의 파일명 충돌은 `409 Conflict`로 분리한다.
- [ ] `.part` 파일 정리 정책, 파일 시스템 잔여 용량, 원자적 `os.replace` 실패 시 오류 응답을 정리한다.
- [ ] 업로드 완료 응답에 서버 파일 식별자·콘텐츠 해시·처리 상태를 포함할지 결정한다.
- [ ] `/health`, 노트 목록/수정 API의 인증·오류 JSON 형식을 클라이언트 계약으로 문서화한다.

### 자체 테스트

- [ ] 정상 M4A 업로드가 `201` 또는 정의된 성공 코드로 저장된다.
- [ ] 같은 바이트의 재시도가 멱등 성공으로 처리된다.
- [ ] 같은 파일명·다른 바이트가 `409`으로 처리되고 기존 파일이 보존된다.
- [ ] 끊긴 전송은 최종 파일을 만들지 않으며 `.part` 정리 정책을 따른다.
- [ ] 토큰 누락/오류, 경로 탈출 파일명, 허용되지 않은 확장자, 초과 용량을 거부한다.
- [ ] 기존 Python 회귀 테스트 전체를 실행한다.

### 이슈 및 대응

- **기존 APK 호환성**: 응답 코드/필드 추가는 허용하되 기존 성공 흐름을 깨지 않는지 별도 호환 테스트를 수행한다.
- **해시 계산 비용**: 서버 저장 후 스트리밍 해시 또는 명시적 헤더 중 구현 단순성과 대용량 파일 비용을 비교해 선택한다.

### 완료 조건

- [ ] 업로드 멱등성·충돌·부분 업로드 회귀 테스트가 자동화되어 통과한다.

## Phase 4 — 사용자 시작형 녹음 Foreground Service PoC

### 목표

Android 14/15 정책 안에서 사용자 조작으로 시작한 녹음이 잠금 화면·앱 백그라운드에서도 안정적으로 이어지는지 검증한다.

### 구현 작업

- [ ] 보이는 Flutter Activity의 녹음 시작 버튼에서만 Kotlin `RecorderService`를 시작한다.
- [ ] `MediaRecorder`를 AAC/M4A, mono, 16kHz, 32kbps 기준으로 구성하고 실제 기기 호환성을 확인한다.
- [ ] microphone foreground service 알림에 녹음 중 표시·정지 action을 제공한다.
- [ ] wake lock은 녹음에 필요한 최소 범위만 사용하고 stop/error 시 반드시 해제한다.
- [ ] 서비스가 예외·권한 취소·저장공간 부족을 감지하면 안전하게 파일을 마감하고 Dart에 오류를 전달한다.
- [ ] 앱 강제 종료, 서비스 종료, 기기 재부팅 후에는 "다시 열어 녹음 시작" UX를 제공하며 자동 마이크 재시작을 구현하지 않는다.

### 자체 테스트

- [ ] Android 14와 Android 15 실제 기기에서 앱이 보이는 상태에서 녹음을 시작한다.
- [ ] 화면 잠금, 홈 전환, 최근 앱 제거 가능 시나리오에서 알림·파일·오디오가 예상대로 동작하는지 확인한다.
- [ ] 마이크 권한을 녹음 중 해제할 때 서비스 종료와 오류 표시를 확인한다.
- [ ] 알림 정지 버튼, 앱 정지 버튼, 예외 종료에서 파일 핸들·wake lock이 남지 않는지 확인한다.
- [ ] 짧은 녹음 파일을 재생해 컨테이너·샘플레이트·음질이 유효한지 확인한다.

### 이슈 및 대응

- **부팅 후 자동 재개 기대**: Android 14+ microphone FGS 제한 때문에 지원하지 않는다. 마지막 상태만 보여주고 사용자가 다시 시작하게 한다.
- **OEM 절전 정책**: 제조사별 예외를 기능 보장으로 취급하지 않고, 진단 화면에서 서비스 종료 사유와 배터리 최적화 안내를 제공한다.

### 완료 조건

- [ ] 대상 Android 버전에서 사용자 시작 녹음, 잠금 화면 지속, 정상 정지 및 오류 회복이 검증된다.

## Phase 5 — 파일 분할, 내구성, 로컬 녹음 저장소

### 목표

장시간 녹음과 중단 상황에서도 손상 파일·누락 파일·중복 업로드를 최소화하는 로컬 데이터 계층을 완성한다.

### 구현 작업

- [ ] 기본 20분, 최소 5분 단위의 청크 규칙과 파일명 규칙(`UTC timestamp + UUID`)을 정의한다.
- [ ] 청크 교체 시 기존 recorder를 먼저 정상 종료·마감하고 검증된 파일만 다음 업로드 후보로 등록한다.
- [ ] 녹음 중 파일에는 `.part` 확장자를 쓰고 완료 후 원자적 rename한다.
- [ ] Room에 recording ID, 파일 경로, 시작/종료 시각, 크기, SHA-256, 상태, 실패 사유, 재시도 횟수를 저장한다.
- [ ] 앱 재실행 시 `.part` 파일과 Room 상태를 대조하여 안전하게 복구·폐기·사용자 안내한다.
- [ ] 저장 공간 사전 확인 및 임계치 경고를 추가하고, 자동 삭제는 명시적 보존 정책 전까지 하지 않는다.

### 자체 테스트

- [ ] 20분 경계 전후 파일이 중복·공백 없이 순서대로 생성되는지 확인한다.
- [ ] 녹음 중 프로세스 종료/저장소 부족/권한 취소에서 `.part`와 DB 상태가 일관되는지 확인한다.
- [ ] 앱 재시작 뒤 완료 파일만 대기열에 남고 손상 파일은 사용자에게 구분되어 보이는지 확인한다.
- [ ] 최소 지원 기기에서 1시간 연속 녹음 시 메모리 증가·파일 크기·배터리 사용을 측정한다.

### 이슈 및 대응

- **기기별 MediaRecorder 차이**: 지원 코덱 고정 실패 시 진단 로그를 수집하고, 후속 버전에서 허용 프로필을 늘린다.
- **파일명 충돌**: 사람 읽기용 시각 외 UUID를 반드시 포함한다.

### 완료 조건

- [ ] 장시간·중단·재시작 테스트에서 업로드 가능한 완료 파일 목록이 일관되게 재구성된다.

## Phase 6 — 전송 대기열, WorkManager, 원격 서버 연결

### 목표

네트워크가 불안정하거나 서버가 멀리 있어도 완료 녹음 파일을 안전하게 전송하고 서버 처리 상태를 확인한다.

### 구현 작업

- [ ] Kotlin `TransferClient`가 Bearer 인증, raw PUT body, 정확한 `Content-Length`, 타임아웃, TLS 검증을 구현한다.
- [ ] 단일 업로드 실패를 예외 삼킴 없이 `failed/retryable` 상태로 기록하고 사용자에게 원인을 표시한다.
- [ ] WorkManager는 네트워크 연결 및 Wi-Fi 우선 제약으로 대기열을 처리한다. 수동 동기화는 사용자가 선택한 네트워크 정책을 따른다.
- [ ] 지수 backoff, 서버의 401/409/413/5xx/timeout별 재시도·사용자 조치 정책을 정의한다.
- [ ] 업로드 성공은 서버가 반환한 파일 해시/식별자와 대조 후 DB에 확정한다.
- [ ] 서버 health 및 노트 API를 주기적으로 조회하되, 녹음 foreground service와 네트워크 작업을 분리한다.
- [ ] LAN URL, VPN URL, Google Cloud HTTPS URL을 동일 설정 모델로 저장하고 인증서 오류를 명확히 안내한다.

### 자체 테스트

- [ ] 로컬 서버에서 새 파일 업로드, 동일 파일 재시도, 파일명 충돌, 토큰 오류를 테스트한다.
- [ ] Wi-Fi 차단, 비행기 모드, 서버 중단, TLS 실패, 앱 재시작 뒤 대기열이 예상대로 복구되는지 확인한다.
- [ ] WorkManager 작업이 정확한 시각 보장이 아닌 최선 노력임을 UI/문서에 표시했는지 검토한다.
- [ ] HTTPS/VPN/원격 테스트 서버로 설정만 변경해 동일 플로우가 동작하는지 확인한다.
- [ ] 업로드 중 앱 프로세스가 종료되어도 다음 실행에서 중복 손상 없이 재시도되는지 확인한다.

### 이슈 및 대응

- **원격 서버는 LAN 서버와 다름**: Flutter 앱이 해결하는 것은 URL 접속이다. NAT, 도메인, HTTPS, 방화벽, Cloud Run/VM/저장소 설계는 인프라 프로젝트로 분리한다.
- **모바일 데이터 비용**: 기본 자동 전송은 unmetered로 제한하고, 사용자가 수동 실행할 때만 예외를 허용한다.

### 완료 조건

- [ ] 네트워크 실패와 재시도에도 서버 파일과 클라이언트 Room 상태가 멱등적으로 수렴한다.

### 이슈 및 대응

- **Play 정책과 사내 APK 요구 차이**: build flavor와 Manifest를 분리해 정책 위험 기능이 공개 빌드에 섞이지 않게 한다.
- **제조사별 서비스 종료**: 지원 기기 목록과 관찰된 제한을 릴리스 노트에 명시하고 자동 재시작 보장은 하지 않는다.

### 완료 조건

- [ ] 승인된 기능만 포함한 release APK, 테스트 결과, 알려진 제한, 롤백/지원 절차가 준비되었다.

## V1 완료 판정표

| 항목 | 완료 기준 |
|---|---|
| 녹음 | 사용자가 시작한 M4A 녹음이 잠금 화면에서도 지속되고 안전하게 종료된다. |
| 복구 | 중단 뒤 완료 파일·대기열·오류가 일관되게 표시된다. |
| 업로드 | 원격/로컬 HTTPS 또는 VPN 서버로 재시도 가능한 멱등 업로드가 된다. |
| 처리 | 업로드 이후 기존 Python 처리 흐름과 노트 조회가 이어진다. |
| 보안 | 토큰·키·TLS 검증이 안전하게 처리되고 민감 정보가 로그에 남지 않는다. |
| 정책 | 부팅 자동 마이크 시작, exact watchdog, 전체 저장소 스캔은 V1에 포함하지 않는다. |
| 배포 | 기존 서명키 없이는 신규 앱 ID의 병행 설치 APK로 배포한다. |

## 출시 전 필수 확인 목록

- [ ] 기존 APK 서명 개인키 보유 여부가 확인되었다.
- [ ] 신규 applicationId 또는 기존 업데이트 전략이 확정되었다.
- [ ] 실서버 URL은 HTTPS 또는 승인된 VPN 경로이고 인증서 검증이 켜져 있다.
- [ ] 서버 업로드 충돌·재시도 계약이 테스트로 고정되었다.
- [ ] 실제 Android 14/15 기기에서 사용자 시작 녹음이 검증되었다.
- [ ] 권한 거부·서비스 종료·네트워크 끊김의 회복 UX가 검증되었다.
- [ ] release APK에 테스트 토큰/cleartext/디버그 설정이 없다.
- [ ] 기존 APK 설치 사용자용 전환 안내가 준비되었다.
