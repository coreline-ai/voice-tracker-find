# implement_20260731_155715.md

작성 일시: `2026-07-31 15:57:15 KST`

이 문서는 현재 5분 녹음에 맞춰진 온디바이스 STT·Gemma 요약 구조를 1시간·2시간
녹음에서도 원문 누락 없이 실행하고, 중단 후 마지막 체크포인트부터 재개할 수 있는
장시간 처리 구조로 확장하기 위한 개발 계획이다.

## 개발 목적

- 1시간·2시간 녹음을 파일 끝까지 스트리밍 STT하고 세그먼트 단위로 즉시 보존한다.
- 앱 화면 이탈, 앱 프로세스 종료, Gemma 작업 프로세스 종료가 발생해도 완료된 STT와
  요약 노드를 잃지 않고 재개한다.
- 긴 전사문 전체를 Gemma에 한 번 전달하지 않고, 입력 한도 안의 계층형 요약 트리로
  처리한다.
- 모든 STT 세그먼트가 정확히 한 개의 1차 요약 노드에 포함되며, 모든 하위 요약이
  최종 루트 요약까지 연결되도록 구조적 범위를 검증한다.
- 내부적으로 여러 구간·장·최종 노드를 만들더라도 사용자에게는 녹음 한 건당 최종 결과
  한 건만 표시한다.
- Gemma 3 1B를 기본이자 유일한 생성형 요약 모델로 유지하고 외부 서버·클라우드·네트워크
  추론 없이 Samsung 실기기에서 검증한다.
- 원본 녹음, 설치 모델, 기존 전사·요약 결과를 삭제하거나 덮어쓰지 않는다.

## 현재 기준선과 구조적 문제

### 확인된 현재 동작

- [x] 완료 녹음 STT는 16 kHz mono PCM을 스트리밍으로 읽고, VAD 기준 최대 28초 구간과
  1초 강제 분할 중첩을 사용한다.
- [x] SenseVoice는 구간별로 인식하지만 전사문과 진단을 모든 구간 처리 후 세션에 한 번
  저장한다.
- [x] STT 품질 실패 시 현재 구조는 전체 PCM을 고정 구간으로 한 번 더 처리할 수 있어
  1시간·2시간 입력에서 처리 시간과 발열이 최대 두 배가 될 수 있다.
- [x] STT·요약 작업은 `viewModelScope`에서 실행되므로 화면 수명주기와 장시간 작업
  수명주기가 분리돼 있지 않다.
- [x] Gemma AIDL은 전사문 전체를 `String`으로 전달하고 서비스에서 10,000자를 넘으면
  거절한다.
- [x] Gemma 입력 생성기는 전체 전사 중 최대 2개 구간·합계 700자만 선택한다.
- [x] Gemma 모델은 요약 요청마다 로드되고 요청 종료 후 별도 프로세스가 종료된다.
- [x] 현재 Room DB는 v8이며 세션·요약 batch·요약 run은 있지만 STT 구간 체크포인트와
  계층형 요약 노드 저장소는 없다.
- [x] Samsung 5분 12.128초 녹음은 1,943자 전사를 만들었고 Gemma 3 1B 실제 요약이
  동일 조건에서 통과한 기준선이 있다.

### 장시간 입력 예상치

아래 값은 현재 5분 12.128초 전사 밀도를 동일하게 적용한 설계용 추정치다. 실제 노드 수와
처리 시간은 Phase 0 Samsung 기준선에서 다시 고정한다.

| 항목 | 5분 12초 기준 | 1시간 예상 | 2시간 예상 |
|---|---:|---:|---:|
| 전사 문자 수 | 1,943자 | 약 22,400자 | 약 44,800자 |
| 현 10,000자 AIDL 허용 여부 | 허용 | 거절 | 거절 |
| 현 700자 입력의 원문 대표 비율 | 약 36% | 약 3.1% | 약 1.6% |
| 700자 이하 1차 요약 노드 최소 수 | 3개 | 약 32개 | 약 64개 |
| 16 kHz mono PCM 크기 | 약 10 MB | 약 115.2 MB | 약 230.4 MB |

### 근본 원인

1. 현재 구조는 “전사 전체 → 대표 근거 2개 → 최종 요약 1회”이므로 녹음이 길어질수록
   대부분의 시간 구간이 최종 입력에서 사라진다.
2. 10,000자 제한만 높여도 700자 대표 추출 제한과 1B 모델의 입력·지시 이행 한계는
   해결되지 않는다.
3. 모든 결과를 메모리에 누적한 뒤 마지막에 저장하므로 중간 종료 시 재사용 가능한
   체크포인트가 없다.
4. 요청마다 Gemma 모델을 다시 로드·종료하는 현재 IPC 계약을 노드 수십 개에 반복하면
   처리 시간·발열·메모리 변동이 과도해진다.
5. `viewModelScope`는 UI 소유 코루틴이므로 1시간·2시간 foreground 처리의 실행 주체로
   사용할 수 없다.

## 핵심 설계 결정

### 1. 사용자 결과 한 건, 내부 처리 노드 여러 건

- 녹음 한 건은 기존과 동일한 `OnDeviceSessionEntity` 한 건으로 유지한다.
- STT 세그먼트와 계층형 요약 노드는 내부 체크포인트로만 저장한다.
- 최종 루트 노드가 품질·범위 gate를 모두 통과한 경우에만 기존 세션의
  `title/summary/selectedSummaryRunId` projection을 한 번 갱신한다.
- 중간 SECTION·CHAPTER 노드를 노트·아카이브의 독립 결과로 생성하지 않는다.

### 2. 고정 3단계가 아닌 입력 한도 기반 재귀 트리

```text
원본 M4A
  → 16 kHz PCM stream
  → STT segment checkpoints (최대 28초)
  → SECTION nodes (목표 3분, 입력 최대 700자)
  → CHAPTER/REDUCE nodes (하위 요약 전체, 입력 최대 700자)
  → 필요한 만큼 REDUCE level 반복
  → ROOT node 1개
  → 사용자 세션 최종 결과 1개
```

- 1차 노드는 목표 3분으로 묶되 `700자` 또는 `4분`에 먼저 도달하면 닫는다.
- 28초 STT 세그먼트 하나가 700자를 넘으면 단어·문장 경계로 하위 조각을 만들고
  원래 시간 범위를 유지한다.
- 상위 노드는 모든 하위 요약을 순서대로 포함하되 canonical 입력이 700자를 넘기 전에
  닫는다.
- 최상위 입력이 여전히 700자를 넘으면 REDUCE level을 추가한다.
- 따라서 2시간을 넘는 입력도 같은 알고리즘으로 처리하며 길이별 별도 코드를 만들지 않는다.
- 700자 상한은 현재 Gemma 3 1B 실기기 성공 기준이다. Phase 0 A/B에서 더 작은 값이
  안정적이면 낮출 수 있지만, 실기기 증거 없이 높이지 않는다.

### 3. 구조적 범위와 의미 품질 분리

- `STT coverage`: PCM 끝까지 처리했는지 여부
- `leaf assignment coverage`: 통과한 STT 세그먼트가 1차 노드에 정확히 한 번 포함됐는지 여부
- `tree coverage`: 각 비루트 노드가 정확히 한 부모에 포함되고 루트까지 도달했는지 여부
- `summary grounding`: 출력 문장이 입력 자식 노드의 용어·숫자·근거와 일치하는지 여부
- 구조적 범위가 100%여도 STT 언어 품질은 `NOISY`일 수 있으며 두 상태를 합치지 않는다.
- 하위 노드 하나라도 누락·실패하면 루트를 `COMPLETE`로 만들지 않고
  `PARTIAL/FAILED_RECOVERABLE`로 저장한다.

### 4. 장시간 실행 주체

- 사용자 조작으로 시작한 장시간 파일 처리는 UI가 아니라 전용 foreground 처리 서비스가
  소유한다.
- Samsung Android 16에서 WorkManager 장시간 Worker가 JobScheduler quota를 사용할 수
  있으므로, 1~2시간 핵심 실행은 direct foreground service를 우선 설계한다.
- Android 15 이상은 로컬 미디어 변환·분석 목적의 `mediaProcessing` service type을
  우선 검토하고, 지원 API별 선언·권한·runtime type을 Phase 0에서 manifest merge와
  실기기 시작 테스트로 고정한다.
- 서비스는 visible UI에서만 시작하고 진행 알림에 일시 중지·재개·취소 동작을 제공한다.
- 서비스 재시작 자체를 데이터 안전성으로 간주하지 않는다. 모든 진행 상태를 Room에
  저장하고 중단 시 `INTERRUPTED`에서 명시적으로 재개한다.

### 5. bounded IPC와 Gemma 배치 수명주기

- 메인 프로세스는 전체 전사문이 아니라 700자 이하의 `nodeId + inputPayload + inputHash`
  한 건씩 Gemma 프로세스에 보낸다.
- Gemma 프로세스는 배치 시작 시 모델을 한 번 로드하고 노드를 직렬 처리한다.
- 각 노드 완료 콜백 직후 메인 프로세스가 Room transaction으로 결과를 저장한 다음 다음
  노드를 요청한다.
- 배치 완료·취소·오류·idle timeout 때 bridge를 닫고 Gemma 프로세스를 종료한다.
- Binder 한 번에 노드 목록 전체나 전사문 전체를 전달하지 않는다.

## 데이터 저장 계약

### 신규 `ondevice_processing_jobs`

- job ID, session ID, source fingerprint, 작업 상태와 현재 단계
- foreground service instance token, operation token
- `total/completed/failed` STT segment 수와 summary node 수
- PCM 준비 상태와 재생성 가능한 job-local 파일 경로
- 일시 중지·취소 요청, 재시도 횟수, 마지막 오류 단계·코드
- 생성·시작·갱신·완료 시각과 checkpoint version

### 신규 `ondevice_transcript_segments`

- segment ID, session ID, pass type, ordinal
- 시작·종료 ms, 원본 범위 hash, 인식 text와 text hash
- raw/정제 의미 문자 수, 인식·품질 상태
- primary/retry provenance와 중복 제거 상태
- `(sessionId, passType, ordinal, sourceRangeHash)` unique key

### 신규 `ondevice_summary_nodes`

- node ID, session ID, batch ID, level, ordinal, node type
- source start/end ms, leaf start/end ordinal, child node ID 목록
- input builder version, input hash, input 글자 수
- 상태, 시도 횟수, 모델·runtime·generation profile
- 요약문, 근거 child IDs, output hash
- 품질 위반 코드, 시작·완료·실행 시간
- `(batchId, level, ordinal, inputHash)` unique key

### 기존 테이블과의 관계

- 기존 `ondevice_sessions`는 사용자에게 보이는 최종 결과와 호환 projection을 유지한다.
- 기존 `ondevice_summary_batches/runs`는 최종 배치·루트 실행 provenance를 유지하고,
  내부 노드는 신규 테이블에 저장한다.
- v8 기존 row는 수정·backfill하지 않는다.
- v9 신규 job부터 계층형 구조를 사용하며 기존 5분 결과는 그대로 읽힌다.

## 상태 전이

```text
QUEUED
  → PREPARING_SOURCE
  → NORMALIZING
  → TRANSCRIBING
  → PLANNING_SUMMARY
  → SUMMARIZING_LEAVES
  → REDUCING
  → VALIDATING
  → COMPLETE

모든 실행 단계
  → PAUSING → PAUSED → 같은 checkpoint부터 재개
  → CANCELLING → CANCELLED
  → INTERRUPTED → FAILED_RECOVERABLE → 사용자 재개
  → FAILED_PERMANENT
```

- terminal 상태만 `operationToken=null`이 된다.
- 취소는 완료된 세그먼트·노드를 보존하되 최종 projection은 만들지 않는다.
- 사용자가 같은 원본을 재개하면 새 세션을 만들지 않고 동일 job의 incomplete 항목만
  처리한다.
- 처음부터 다시 실행은 명시적 사용자 동작으로 새 batch를 만들고 기존 체크포인트를
  삭제하지 않는다.

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트와 완료 조건을 통과한 뒤 시작한다.
- 구현 중 발견한 문제와 수정 결과를 해당 Phase의 `이슈 및 수정`에 기록한다.
- 체크박스는 실제 코드·테스트 상태와 동시에 갱신한다.
- 원본 M4A와 설치 모델은 읽기 전용으로 취급한다.
- 모델·원본·기존 세션은 사용자의 명시적 삭제 전까지 유지한다.
- 원문과 모델 raw output을 logcat, 테스트 stdout, PC 증적, 계획 문서, 서버에 기록하지 않는다.

## 잔여 리스크 / 후속 과제

- SenseVoice가 파일 끝까지 처리해도 고유명사·구어체·잡음 인식 정확도는 별도 품질 문제다.
  장시간 구조 완료와 STT 모델 정확도를 같은 성공 지표로 합치지 않는다.
- 계층형 요약은 모든 구간의 구조적 포함을 보장하지만 모든 세부 사실이 최종 한 문장에
  남는 것을 보장하지 않는다. 최종 UI에 장·구간 근거를 접어서 확인할 수 있게 유지한다.
- 반복되는 5분 scale fixture는 시간·복구·자원 검증에는 유효하지만 다양한 주제의 의미
  품질을 대표하지 않는다. 별도 정답 transcript/audio fixture가 필요하다.
- Android 16의 장시간 실행 quota와 foreground service 제한은 OS 업데이트에 따라 달라질
  수 있으므로 target SDK 변경 때 공식 문서와 실기기 gate를 다시 실행한다.
- 2시간을 크게 넘는 입력은 같은 재귀 트리로 처리할 수 있지만 battery·thermal·사용 시간
  SLO는 별도 4시간 이상 soak test 후 지원 범위를 확정한다.
