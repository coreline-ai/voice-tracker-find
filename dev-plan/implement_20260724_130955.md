# implement_20260724_130955.md

작성 일시: `2026-07-24 13:09:55 KST`

이 문서는 삼성 실기기에서 녹음한 파일이 맥미니 LAN 수신기에서 처리되고,
STT/노트 생성 후 앱의 두 번째 탭으로 다시 내려오는 완전한 1회 E2E를 고정하기
위한 작업 문서다.

## 개발 목적

- Samsung SM-S931N에서 실제 녹음 1건을 생성한다.
- Wi-Fi LAN으로 업로드하고 앱에서 업로드 완료 상태를 확인한다.
- 맥미니의 기존 로컬 파이프라인이 VAD → STT → LLM/노트 생성을 수행하도록 실행한다.
- 앱이 생성된 노트를 다시 동기화해 두 번째 탭에 표시하는지 확인한다.
- 실패 지점을 재현 가능한 로그·파일·상태값으로 남기고, 수정 후 동일 시나리오를 재실행한다.

## 최종 E2E 증적

- 대상: Samsung `SM-S931N`, Android `16` / API `36`, 무선 ADB `192.168.0.75:5555`
- 앱: `com.thinktank.recorder.next.debug`, `versionCode=1`, `versionName=1.0.0-debug`
- 최종 파일: `rec_20260724_043957_8cb289ed-6a8b-4694-9206-f87b0fec5fc0.m4a`, `121,449` bytes
- Samsung 내부 파일과 서버 inbox SHA-256: `beab7c30ad2ae191ab86f6f74d2d30d6b8cd9d0af456653c477596ccc210700b` (일치)
- 앱 1차 업로드 결과: `동기화 완료 · 녹음 1개 전송 · 노트 0개 확인`
- 서버 자동 처리: `RECEIVER_AUTO_PROCESS=1`, 13:43:29 트리거, VAD/STT/LLM/Obsidian 완료, `1건 성공 / 0건 실패`
- 생성 노트: `10-daily/2026-07-24_중요.md`, 모바일 API 노트 4개
- 앱 2차 동기화 결과: `동기화 완료 · 녹음 0개 전송 · 노트 4개 확인`
- 앱 본문 확인: `2026-07-24 중요` 상세 화면에서 `실기기-공개: 중요한 실기기 공개 관련 언급...` 본문 표시
- 중복 검증: 재동기화 후에도 `녹음 0개 전송`으로 중복 업로드 없음. 서버 inbox `queue.count=7`은 처리 완료 파일을 retention 기간 동안 보존하는 값이고, 앱 업로드 대기 `0`과 같은 의미의 pending count가 아니다.
- 회귀 테스트: Android `BUILD SUCCESSFUL`; Python `621 passed, 12 skipped, 4 deselected`

## 잔여 운영 리스크

- 서버는 현재 평문 HTTP(`tlsEnabled=false`)다. 동일 AP의 개발망 검증용으로만 사용하고, 외부망/운영 전환 전 TLS와 인증서 피닝을 적용해야 한다.
- 수신기 자동 처리 debounce는 150초다. 업로드 직후 앱에는 업로드 완료가 먼저 표시되고, 노트 생성은 최대 약 150초 뒤에 완료된다.
- 모바일 노출 정책상 `20-notes` 및 `기타` 일일 노트는 앱 목록에서 제외되고 볼트에만 남는다. 앱에서 즉시 확인하려면 중요/일정/위키/아이디어 분류를 사용해야 한다.
- 대시보드의 `queue.count`는 현재 inbox 보존 파일 수를 의미한다. 운영 화면에는 향후 `pending/processed/no_speech/failed`를 분리해 표시하는 후속 작업이 필요하다.
- 이번 실기기 테스트는 시간 제한상 `WHISPER_MODEL=tiny`를 사용했다. 운영 STT 기본값 `large-v3`의 품질·처리시간은 별도 운영 검증이 필요하다.
- 회귀 빌드 후 최종 APK 재설치 시점에는 삼성폰 Wi-Fi ADB 호스트가 offline/host down으로 전환됐다. E2E에 사용한 동일 `1.0.0-debug` APK는 그 이전에 무선 설치·실행되어 있었고, 이후 소스 변경은 계획 문서뿐이다. 다음 실기기 작업 전에는 Wi-Fi ADB를 다시 연결해야 한다.
